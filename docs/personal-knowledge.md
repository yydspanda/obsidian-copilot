# Personal Knowledge Studio

Knowledge Studio is the Windows desktop workspace for the personal knowledge system being built into this Copilot fork. It is designed to make long-running ingestion, multi-file review, and recoverable knowledge maintenance understandable before any generated page is written.

## Platform and availability

The Knowledge Studio view and ribbon entry are available only in Obsidian Desktop on Windows. Open it from the library icon in the ribbon or run **Open Knowledge Studio** from the command palette. The command remains registered on other platforms so it can explain that the feature is unsupported; it does not open the Studio there.

The rest of Copilot keeps its existing platform support. The plugin manifest therefore remains compatible with mobile and other desktop systems; the Knowledge Studio view and navigation are not registered outside Windows. This avoids disabling Chat for existing users while the new filesystem and recovery adapters are deliberately tested on Windows first.

The current milestone exposes a fail-closed Studio shell and the review/activity foundations. On supported Windows desktop installations, the plugin now attempts to initialize and validate a private `knowledge-runtime-v1.json` state foundation beside the plugin files. The filename remains stable while its internal format is explicitly versioned; the current outer format is version 3.

After Obsidian reports that the Vault layout is ready, a plugin-level startup barrier checks the Runtime, waits for Projects to finish loading, and strictly validates every project-owned Knowledge Bundle as one Windows write-boundary set. The Studio uses one stable delegating port across this lifecycle, so an already-open view cannot retain an obsolete adapter. Missing, invalid, or conflicting configuration receives an explicit unavailable explanation. Even valid configuration remains **Adapter unavailable** because the production recovery validator, file resolver, watcher, compiler, worker, and query adapters are not connected yet. This prerequisite barrier does not run the internal startup recovery Gate or release a Queue. The shell shows no fabricated jobs, does not call a model, and cannot change knowledge files.

An independent Vault source-watcher adapter is now implemented and tested, but it is intentionally not activated by plugin startup yet. It accepts only an immutable plan of already-registered sources and pipeline fingerprints. For an initial scan, create, or modify event, it captures the path and a retry-stable capture id synchronously, durably allocates the source revision, then reads exact binary bytes from the exact owning App, Vault, and data adapter, locally verifies the unnormalized-byte hash, and submits only through the source-observation hand-off. It also rejects mismatched allocation or settlement identities returned by an adapter. Retries reuse the same capture, token, hash, and pipeline identity; an old plugin or plan generation cannot continue to read, commit, or publish after replacement. A companion exact-byte reader can reject a Queue job whose current file hash changed before any future parser or model call, while returning the same verified bytes that the parser must consume.

This foundation does **not** mean files are currently being watched in the background. A durable source-identity/watch-plan builder, restart recovery for allocated and bound observations, startup Gate/release composition, and the real parser/compiler worker still need to be connected first. Rename and delete also remain fail-closed: the adapter never turns them into an empty-file observation, immediately invalidates in-flight work for the affected plan, and quarantines the source so a new file at the old path cannot inherit the old source identity. Only an explicitly replaced and revalidated watch plan can resume that source. Studio therefore remains **Adapter unavailable**, and this milestone still performs no model call or Wiki write.

Project discovery is isolated to the current plugin and Vault lifecycle. During a plugin reload or Vault change, old project listeners and subscriptions are retired before the new project snapshot is installed. A scan or file operation that finishes late cannot republish its result into the new snapshot, and an old cleanup cannot release a newer write guard for the same path. Changing the configured Projects folder also invalidates old-folder scans, file events, and project edits synchronously; if a current-folder event wins a scan race, a trailing full scan converges the snapshot. This keeps Bundle discovery from inheriting stale or mixed Projects state across reloads and folder changes.

The internal safety core now carries a complete, content-addressed Manifest plan from compilation through durable review; the plan-bound final intent and plan digest then enter the transaction journal. Review filtering or content edits produce a new exact final projection instead of guessing from only the files that changed. Queue v5 keeps the accepted ChangeSet and final Manifest-intent identities with the exact applying claim, plus an append-only record when a user explicitly abandons an apply before journaling. Before a new apply can even inspect a target Wiki file, the runtime rechecks the Queue claim, full accepted Review payload and intent, source high-watermark, input-revision allocator, current Manifest read-set, and source commit ordering. Prepared-journal publication repeats that proof atomically, and the same complete reservation is preserved when the journal enters applying, whenever unfinished work is read during startup, throughout shared runtime updates while it is active, and before Manifest success and its replay ledger are published. A v3 reviewed apply that lacks the new intent identity, or a transaction whose Manifest read-set has drifted, is therefore blocked before any new Wiki file access rather than guessed into valid authorization. Retained reruns must describe the latest source observation, and a pending Queue commit marker must match the exact success ledger even after the active journal has been acknowledged. Exact ledger retry remains a byte-preserving no-op, while conflicting identity fails closed. Startup also cross-checks the Manifest, reserved commit metadata, latest ledger proof, Queue commit marker, and shared-page co-owner state. Shared pages update every recorded co-owner hash in that same operation. These guarantees are implemented and tested as foundations, but they do not make the unavailable Studio workflow usable yet.

The runtime foundation has automated contract and filesystem tests, but it has not yet passed acceptance inside a real Windows Obsidian test Vault. In particular, Obsidian process serialization, plugin reloads, external editor races, NTFS/OneDrive behavior, and crash persistence still need real-device verification. It must not be treated as production-ready durable storage yet.

## Project Bundle configuration

Knowledge Bundle configuration is stored in the owning project's `project.md` frontmatter. The Projects layer preserves this value as untrusted data; only the knowledge startup boundary parses it. It never repairs paths or silently drops unknown fields.

```yaml
copilot-project-knowledge-bundle:
  version: 1
  id: research
  sourceRoots:
    - Sources/Research
  wikiRoot: Wiki/Research
  schemaRef: Knowledge/Schemas/research.md
  reviewMode: always
```

The object is strict: it accepts only the six fields shown above, requires at least one source root, and supports `always`, `multi_file`, or `trusted_generated_only` as the review mode. Review modes do not authorize automatic writes in the current unavailable milestone.

All paths must be canonical Vault-relative paths using `/`. Absolute paths, drive letters, UNC paths, backslashes, `.` or `..`, Windows-reserved names, invalid characters, and trailing dots or spaces are rejected rather than rewritten. Source roots must be unique under Windows case-insensitive comparison and must not overlap their Wiki root. A schema cannot live inside a generated Wiki.

Validation covers all configured projects together. Bundle IDs must be unique; Wiki roots cannot overlap one another; no Bundle's Wiki may overlap another Bundle's source roots; and no Bundle's schema may live inside another Bundle's Wiki. One invalid configuration keeps the whole knowledge workflow unavailable so two projects can never acquire ambiguous write ownership. If no project has this field, Studio reports **Bundle unconfigured**. If several valid Bundles exist, validation succeeds but the current milestone does not choose one implicitly; Studio remains unavailable until an explicit Bundle selector is added. Configuration changes currently require a plugin reload before this startup-only check runs again.

## Activity

The following Activity behavior is implemented in the core and UI, but the unavailable Studio shell does not yet load real jobs. Activity is designed as a read-only projection of the durable ingest queue. It distinguishes parsing, analysis, association, generation, validation, review, apply, and final commit acknowledgement.

- **Pause** and **Resume** control whether the Bundle may start new work or accept a review. A transaction already applying is allowed to reach its recoverable commit boundary and is not interrupted halfway.
- A Queue held by **Startup recovery** cannot be cleared by ordinary Resume, another Pause, or a sequence of low-level Queue updates. Startup, interrupted-apply, and commit-acknowledgement recovery gates preserve the current claim, job, pending-review anchor, and commit marker; an accepted review waiting to start is protected in the normal running state too. Transitions must match the exact current recovery operation, so an older successful ingest or a fabricated abandonment cannot replace the interrupted decision. A source capture now receives a globally unique retry-stable capture id, opaque token, and durable revision before asynchronous reading; the exact content hash and pipeline are then bound first-write-wins. The production Queue adapter can advance a high-watermark only when given that private token, consuming the exact binding in the same runtime-file update. A newer allocation that has not completed reading does not discard an older bound read, while a newer completed binding supersedes older unfinished observations. Pending allocated and bound work can be enumerated after restart; historical consumed retries return their own durable result without entering Queue again. A bound observation that has not reached Queue also blocks startup release. Only the conditional startup release can change the final startup gate to running after rechecking the shared durable state.
- **Cancel**, **Retry**, and **Review** are shown only when the selected job allows them.
- A job awaiting review cannot use generic **Cancel**. It must be accepted or durably rejected from Review so its proposal outcome and any retained rerun stay consistent.
- A job being applied cannot be cancelled from the Activity panel.
- A committed job remains **Finalizing** until its durable commit marker has been acknowledged. It is not shown as completed early.
- A divergent interrupted write is shown as **Recovery required** and automatic writes remain blocked. This milestone shows the blocker but does not yet expose revalidate, continue, rollback, or abandon actions.

Activity notifications only request a fresh durable read. They never promote a job optimistically.

## Change review

The following Review behavior is implemented in the core and UI, but it is not yet connected to a live Windows workflow. Review presents one proposed ChangeSet across all of its files. Create and update proposals can be accepted exactly, rejected, or decided block by block. Batch actions still respect every file's capability: **Accept all** cannot override a blocked target.

The review surface sends only content-addressed snapshot identity plus opaque ChangeSet, file, and block identifiers back to the core. It never sends file paths, edited content, file before/after hashes, validation flags, or a claimed status. The core reconstructs the exact selected content, recalculates hashes, and runs deterministic validation again.

The complete proposal is persisted in the Review Store before the queue can wait for review. Accept or Reject then persists an exact terminal Review Store record before the queue changes state. Refreshing the same acceptance while its apply claim is still active is safe and does not create another claim; a conflicting receipt is blocked. After an apply is fully finalized, a late acceptance is not applied again and will be handled by the future Review/Manifest reconciliation flow.

For this milestone, a successful source commit must be backed by that durable accepted Review record. The configured auto-review modes are not allowed to publish knowledge success until a separate durable policy authorization is implemented; an in-memory policy decision is not sufficient.

Delete proposals are visible with a danger explanation but are rejection-only in this milestone. The Windows file store advertises `delete: false`; it can recognize an already-missing replay or a conflicting third state, but it never performs a delete. Manifest ownership, source provenance, and last-generated hashes are now journaled and revalidated, but delete acceptance stays disabled until a safe compare-and-delete implementation and the remaining schema/link/source-artifact dependencies are also revalidated immediately before write and recovery.

Rejecting a proposal does not create an empty accepted ChangeSet and does not write files. Its durable rejection identity remains available for safe retry and audit.

## What comes next

Startup reconciliation for persisted work now has a pure orchestration gate, but the new plugin startup barrier deliberately does not invoke it yet. The outer barrier only proves Runtime, Projects, and aggregate Bundle configuration prerequisites. Given a strictly validated current Bundle and the still-missing production recovery adapters, the inner gate can recover the Queue, roll forward only an already-journaled transaction and its commit bookkeeping, reconcile pending or rejected Review hand-offs, and then read the Queue, the Vault-global transaction slot, and every accepted Review classification from one runtime-envelope snapshot. A Review revision change restarts this bounded pass. Runtime and Queue observations may only advance; a rollback or different Queue content at the same revision fails closed. Every accepted Review action must also correlate one-to-one with exactly one classification through its opaque recovery id. The first file-state conflict is persisted as sticky recovery state and immediately re-read as the same visible blocker.

Accepted reviews are never started or applied automatically by this gate. The real pipeline test now also covers an accepted Review before apply starts and proves the safely paused runtime bytes and Wiki remain unchanged. An explicit exact acceptance may establish its apply claim while leaving the startup gate paused; this does not release unrelated backlog. If that claim exists but no journal was ever published, the core requires an explicit **Continue** or **Abandon** decision. Continue reloads the accepted content and rechecks the current Manifest before the transaction may inspect Wiki files. Abandon is allowed only when the same atomic update proves that no active journal, commit marker, or source-input success ledger exists; it keeps the accepted review as immutable history. A stale Manifest blocks Continue but does not fabricate evidence that Wiki writes began.

An `observed_clear` gate result is only an optimistic display observation. The new conditional release core carries its Runtime, Review, and Queue revisions into one shared-envelope update, where it rechecks the Vault-global transaction, recovery markers and claims, interrupted apply work, cross-Bundle write-recovery evidence, and every accepted Review classification. Only `committed` or `abandoned` accepted records are terminal. Success changes only the exact `startup_recovery` Queue control and the Queue/Runtime revisions; stale or blocked attempts preserve the runtime file bytes. If the write committed but the caller observed an error, the old token is deliberately not treated as a receipt: startup must run again and the fresh observation will see the Queue already running. Existing user or rate-limit pauses are never overwritten.

These actions, the gate, and release are tested but do not appear in Studio yet. The plugin-level prerequisite barrier now keeps Studio unavailable, but there is intentionally no worker to release. Future production composition must run the inner Gate and conditional release for every configured Bundle before installing a ready delegate; an empty/running Queue or a retained user/rate-limit pause is not by itself proof that startup coordination ran.

Only a provably idle legacy runtime is upgraded automatically. A legacy file containing active/recovery work, prior Manifest success, an apply abandonment, or reserved commit metadata is kept byte-for-byte and loading fails closed rather than guessing it into the new format; a user-facing recovery path is still future work.

The next implementation steps are connecting the real Windows watcher to the new source-observation hand-off, rechecking artifact bytes before compilation, composing the production recovery/file/compiler adapters behind the existing startup barrier, running the inner Gate and conditional release per Bundle, adding Bundle selection and a Studio recovery screen, defining durable `no_changes` success semantics, authorizing any future auto-apply policy durably, completing the schema/link/source-artifact read-set, coordinating Queue/Review/observation history retention, connecting real parser/provider/compiler adapters, adding Chat's **Add to Knowledge** entry, grounded query/citation navigation, and end-to-end testing in a dedicated Windows Vault. The Studio should not be treated as a finished ingestion workflow until those integrations and tests are complete.
