# Personal Knowledge Studio

> 中文用户请从 [Personal Knowledge Studio 中文使用手册](knowledge/zh-CN/index.md) 开始。它按实际操作拆分了快速开始、配置、导入、Activity、Review/Apply、Query、维护、安全与故障排查；本页保留完整的技术边界和验收背景。

Knowledge Studio is the Windows desktop workspace for the personal knowledge system being built into this Copilot fork. It is designed to make long-running ingestion, multi-file review, and recoverable knowledge maintenance understandable before any generated page is written.

## Platform and availability

The Knowledge Studio view and ribbon entry are available only in Obsidian Desktop on Windows. Open it from the library icon in the ribbon or run **Open Knowledge Studio** from the command palette. The command remains registered on other platforms so it can explain that the feature is unsupported; it does not open the Studio there.

The rest of Copilot keeps its existing platform support. The plugin manifest therefore remains compatible with mobile and other desktop systems; the Knowledge Studio view and navigation are not registered outside Windows. This avoids disabling Chat for existing users while the new filesystem and recovery adapters are deliberately tested on Windows first.

The current milestone exposes a live Studio over the durable Runtime after startup safely admits one uniquely selected Bundle. On supported Windows desktop installations, the plugin initializes and validates a private `knowledge-runtime-v1.json` state foundation beside the plugin files. The filename remains stable while its internal format is explicitly versioned; the current outer format is version 9. Version 4 introduced the exact Apply/no-change completion-proof fence, and version 5 introduced the protected source-retirement tombstone and its downgrade fence. Later migrations, including the current version 9 format, retain that proof while adding newer durable authorities. Older migrations still conservatively return unproved reusable completions to pending recovery work rather than guessing success. Activity and pending Review data are real durable state, not demo fixtures. The live command subset is deliberately narrow: folder-only external source import; explicit Vault-source registration and reviewed Chat Knowledge Draft capture; Activity Pause, Resume, Cancel, and Retry; Review Reject; explicit reviewed create/update acceptance and Wiki Apply; the limited Recovery actions described below; Bundle-scoped grounded Query with exact Markdown and raw-byte-verified PDF page citation navigation; reviewed **Save to Wiki** capture for an eligible current answer; and exact-path source recheck plus twice-confirmed source retirement. Wiki delete acceptance and every automatic acceptance or Apply policy remain fail-closed.

The missing-source round trip and twice-confirmed retirement of a disposable source have passed bounded Windows acceptance; only the physical right-click warning remains automated-only. A recoverable missing, delete, or rename affects only that source and appears in **Sources**. An already-open Sources view refreshes from Ready to Missing when the issue is observed, and returns to Ready only after the exact registered path has been restored and its capture has settled. Recovery requires restoring that exact Vault path and choosing **Check again**; the command never creates, copies, moves, or overwrites a file, and there is no arbitrary replacement-path UI. If startup is held by the exact combination of same-Bundle recoverable missing-source evidence and a pending source observation, Studio exposes a least-authority Sources-only recovery view before Queue release. That view permits only source inventory, recheck, and retirement; worker/model, Query, Review, Apply, and Wiki capabilities remain unavailable.

**Remove** uses the protected retirement tombstone introduced in Runtime v5 and still retained by the current Runtime v9; it is not a file deletion. It leaves source and generated Wiki bytes untouched, removes only active Manifest membership and provenance authority, preserves Queue, Review, and Apply-ledger history, atomically terminalizes the target source's allocated or bound observations, and reserves its identity and path against silent re-registration. Real active Queue, pending Review/Apply, Recovery, transaction, or rerun work can still block retirement; the target allocated/bound observation is not itself a permanent blocker. Obsidian's file-menu integration is advisory navigation only; it cannot intercept keyboard or Windows Explorer deletion.

After Obsidian reports that the Vault layout is ready, a plugin-level startup barrier checks the Runtime, waits for Projects to finish loading, and strictly validates every project-owned Knowledge Bundle as one Windows write-boundary set. The Studio uses one stable delegating port across this lifecycle, so an already-open view cannot retain an obsolete adapter. Missing, invalid, conflicting, or multi-Bundle-without-selection configuration is projected into a guided local setup surface rather than requiring the user to infer the cause from one generic unavailable page. A valid configuration also runs a synchronous production preflight over the exact Bundle owners, current Projects/settings snapshot, reviewed parser/compiler profile, selected DeepSeek V4 model, hydrated credential, and the plugin renderer's native-fetch capability. Preflight constructs an isolated Compiler route and a separate read-only grounded-answer route under the same generation-owned lease; it never invokes fetch. Startup then consumes one recovery-only capability over that exact Runtime, Vault, and Bundle generation. A Vault-global active transaction owner is recovered first; the Gate may reconcile already-durable Queue/Review bookkeeping and roll forward only an already-persisted, already-authorized transaction journal. Settings, Projects, Runtime, replacement, or unload invalidation is rechecked between durable recovery phases, so an obsolete generation cannot finish Queue recovery and then begin a Wiki transaction. A phase that already entered durable reconciliation is allowed to reach its crash-safe boundary before later phases stop. The Gate itself cannot release the Queue, claim new work, choose a no-journal recovery action, prepare a new transaction, start a watcher or worker, or call a model. **Recovery needs attention**, **Recovery blocked**, and recovery failure remain separate fail-closed states. An `observed_clear` result starts the later observation, fresh-Gate, and conditional-release handshake; only successful admission can start the production worker and publish its same-generation Studio adapter. For one valid Bundle, Studio then reports live durable Activity and Review and exposes only the narrow command subset described below.

The **Setup & status** surface is a separate, presentation-only readiness authority. It consumes the startup barrier's typed, sanitized state and a reason-only projection of the currently selected ordinary Chat model, then publishes monotonic immutable snapshots with three independent lanes: Workspace, the Project-owned Knowledge model, and optional ordinary Chat. Chat readiness never downgrades Knowledge readiness. **Configured locally** proves only the local catalog/configuration and credential-presence checks represented by those inputs; it never means online, connected, quota-valid, credential-valid, or local-server reachable. Passive rendering and refresh perform no provider request or model invocation. Its commands are least-authority navigation only: open the current unambiguous Project or Schema, open existing Chat or Copilot settings, or refresh the displayed local projection. They cannot create a Project, directory, or Schema, mutate Bundle YAML, select a model, store a key, or repair durable state. Opening the existing Copilot settings surface may independently run that surface's plugin-update check; that is not provider verification. Recovery and missing-source startup states keep their established Recovery or Sources surfaces and are not converted into setup automation.

An independent Vault source-watcher adapter, strict plan builder, read-only workflow-plan loader, listener-first observation-startup Core, and job-bound model-adapter core are now implemented and covered by automated tests. After recovery is clear, the plugin startup barrier creates the same-generation production observation session and retains its live watcher. The watcher no longer accepts a caller-created list of paths and hashes. The loader builds its opaque plan from strictly detached Bundle and current Manifest snapshots, exact schema bytes, the reviewed parser registry, and a projected model behavior profile. The production composer binds those inputs to the exact preflight generation and a startup-held Queue. It establishes listeners before its crawl, reconciles recoverable allocated and bound observations, performs an authoritative full scan, waits for captures to settle, and can repeatedly re-prove the live session. Once convergence is proven, the session performs a fresh observation reproof, reruns the startup Gate, and conditionally releases the Queue only when the Runtime's atomic authority proof succeeds for every configured Bundle. The plugin then installs the same-generation production worker. It drains released Queue work, reads and parses the exact authorized source bytes, runs the two-stage DeepSeek compiler, validates the complete candidate, saves the proposal to the same Runtime's durable Review Store, and only then moves the Queue job to `awaiting_review`. Model selection is exact and never falls back to a different chat model. Only an explicit behavior allowlist is retained; API keys, complete settings, unknown model fields, and credential-like compiler or parser configuration are not included. Endpoint and routing values are retained only as plaintext-free SHA-256 identities; these hashes are not credentials, and low-entropy values may still be enumerable.

Plan construction verifies that every registered source remains inside an authorized source root, never ingests its generated Wiki or schema, and maps to exactly one configured parser. Each source fingerprint binds the exact Bundle-config digest, compiler version and configuration, selected parser identity and configuration, exact schema hash, projected model behavior, output language, OKF version, and citation contract. The plan also binds the selected parser profile, Manifest revision and digest, and submitted profile digest without exposing schema content, settings, App/Vault services, or parser capabilities. The loader reads all Bundle authorities twice and publishes a plan only when both complete projections match. An opaque execution owner is registered exclusively to one Runtime and one workflow-loader generation, so equal data or deliberate reuse of the same owner cannot join different lifecycles. This detects changes during collection but is not a cross-Bundle database transaction, so the owning workflow generation must still invalidate the plan whenever Projects, settings, Runtime, App, or Vault ownership changes.

Before a source is parsed, Queue now issues an opaque process-local claim bound to the exact active controller, attempt, QueueStorage facade, and Queue-owned cancellation signal. Runtime accepts that claim only through a narrow proof facade and reads the unique processing Queue job, exact consumed source observation, and current Manifest from one atomic envelope. A scalar high-watermark or a migrated legacy checkpoint is not sufficient. The authorization binder then compares Runtime's Manifest authority with the workflow plan before any source read. The plan rechecks the current Manifest, exact schema bytes, and secret-free pipeline profile, asks the exact-byte reader to prove the source hash, and repeats those authority reads after parsing. Only this Runtime-to-workflow-to-Runtime proof sandwich can upgrade parsed material into an opaque compiler preparation; a job-shaped object, copied prototype, or `unbound_read_only` marker cannot do so.

The same returned byte array is passed to a Knowledge-specific parser; the existing general file parser is not reused because it can reread paths or use caches and external services. The built-in text parser accepts bounded, non-empty UTF-8 for explicitly configured suffixes. It preserves BOM, CRLF, Chinese, and other Unicode text byte-for-byte and rejects malformed UTF-8. The built-in PDF parser copies the already-verified raw bytes before handing them to Obsidian's public local PDF engine, then extracts bounded text in deterministic item order for each 1-based page. Its durable artifact hash remains the SHA-256 of the original PDF bytes, not a converted-text or cache hash. The parser profile binds the extraction contract and current Obsidian API version; malformed, encrypted, image-only, empty-text, and over-limit PDFs fail closed without OCR or an external service. The execution binding detects byte changes that remain at its parser-boundary checkpoints; parser registration and fingerprinting do not sandbox an untrusted parser or detect a mutate-then-restore implementation. Production composition must therefore use only owned, reviewed parser capabilities. Other binary formats remain unsupported. PDF page navigation stays a separate read-only capability: an accepted locator must still re-prove the exact raw PDF hash before and after opening its page.

The Knowledge-specific model adapter accepts only that authentic preparation, its exact Queue signal, a matching secret-free model profile, an opaque private route capability, and a one-shot call authorization issued internally by the Compiler for the exact request. One authorized preparation can create only one adapter. Every `compile()` invocation receives a fresh opaque session: the adapter pins it during analysis, and generation must present the same identity, preventing duplicate adapters, cross-Compiler, cross-compile, and replayed stage composition. Credentials, endpoint text, and the transport closure remain in module-private memory; the public route exposes only its detached profile declaration. The complete configuration digest binds model parameters plus endpoint/routing identities. A concrete route can additionally bind the complete pipeline profile so output language, compiler/parser behavior, OKF, and citation-contract changes cannot reuse an otherwise identical model route. For each authorized stage, the adapter makes one outer route invocation, re-proves authority before and after it, accepts only bounded JSON text, parses it inside the private boundary, and returns a detached bounded object to the Compiler's strict schema parser. A fresh adapter pins the first authentic Compiler session it receives, so it remains a trusted assembly capability until that first call. The production composer now constructs the exact Runtime-owned Review repository internally and hands the adapter directly to its intended Compiler; an opaque execution-owner brand prevents a Queue/preparation/handler/Review composition from crossing Runtime generations.

Isolated DeepSeek routes and deterministic Knowledge prompt encoders are now implemented. They are not shared with Chat, LangChain, `safeFetch`, or Obsidian `requestUrl`. Both routes accept only the reviewed official `https://api.deepseek.com/chat/completions` endpoint and the current `deepseek-v4-flash` or `deepseek-v4-pro` model identities. The Compiler and grounded-answer paths share reviewed HTTP mechanics but have separate prompts, request authority, response schemas, and lifecycle ports. Saved direct-DeepSeek `deepseek-chat` and `deepseek-reasoner` entries are retained as disabled migration markers, and an old chat, command, or project reference is never silently redirected. Each authorized call uses an injected native-fetch-compatible port with its exact cancellation signal, `stream: false`, no tools, no fallback, no repair, no internal retry, and `response_format: { type: "json_object" }`. DeepSeek JSON Object mode is not a native JSON-Schema guarantee: versioned prompts specify the expected shape while strict Core schemas remain authoritative. Source text, schema text, existing Wiki content, user questions, evidence, and output-language values stay inside canonical escaped `INPUT_JSON`; they never become system-message instructions. The response is counted from its first byte, including non-stream keep-alive whitespace, capped before fatal UTF-8 decoding, and accepted only for one exact-model choice ending in `stop` with bounded token usage. Thinking mode rejects configured `topP` and requires an explicit zero temperature placeholder, then omits both sampling fields from the wire because DeepSeek does not support them in that mode; non-thinking mode may send the validated sampling fields. Fenced JSON, redirects, SSE, truncated output, tool calls, old model aliases, custom endpoints, and unsupported settings fail closed. Sanitized transport categories cross the private boundary without retaining provider payloads or causes. The transport itself retries nothing. See the current [DeepSeek Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion/), [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/), and [JSON Output](https://api-docs.deepseek.com/guides/json_mode/) contracts.

Preflight, both startup Gate passes, and passive Setup-readiness projection perform **zero model-provider network requests**. This does not make the released workflow offline: after conditional release, a queued source can be parsed in the background and normally makes one authorized DeepSeek analysis request; only analysis that authorizes writable targets proceeds to a second generation request. The source material, schema policy, and any authorized existing target content needed by compilation leave the local machine. A grounded Query additionally sends the user's question, bounded applied-Wiki context, and eligible exact `.md` source excerpts in one separate DeepSeek request and may incur provider charges. A Query with no eligible source evidence returns **Insufficient evidence** without calling the model. The API key remains inside private route memory and is never written to a descriptor, result, prompt, error, log, Review record, or durable Runtime file. A user who follows a Setup navigation action into the existing Copilot settings page may separately trigger that page's plugin-update check; this is outside passive readiness projection and is not a provider or credential test.

The released worker stops at a durable proposal. It has no Review-decision, Wiki mutation, or Apply capability, never auto-accepts a proposal, and cannot start a fresh Wiki transaction. Explicit user acceptance goes through a separate generation-owned Studio coordinator, so connecting reviewed Apply does not broaden the background worker. The same-Runtime Review record is persisted before the Queue enters `awaiting_review`. Studio now reads Queue and Review together from one atomic Runtime projection and displays only pending records whose durable Queue anchor, job claim, proposal digest, record revision, and timestamp all agree. It then resolves the current Wiki targets and repeats the outer Runtime revision read; concurrent Runtime or target-state drift causes a bounded full retry instead of a mixed snapshot. Runtime commits and changes beneath the Bundle's Wiki root produce reload hints only—the next durable read remains authoritative. Recoverable missing/delete/rename state remains an authoritative blocker for the affected source plan but is projected through **Sources** instead of making the whole Studio unavailable. Exact-path case mismatch, a Windows path-key collision, capture failure, or an unsettled fatal observation still fails closed. Closing, superseding, or invalidating a generation synchronously withdraws the live Studio delegate, removes its Runtime/Vault reload listeners, and aborts the exact Queue-owned signal and any native fetch still using it. Ordinary supersession or invalidation then exposes only the neutral, action-free refreshing state until a freshly admitted generation starts; plugin unload or a persistent startup failure keeps the controller unavailable and the UI on its guided local-status surface. Neither path retains stale Activity as authoritative. Non-applying work is returned to durable startup recovery, while an already applying transaction remains protected until its crash-safe boundary. When durable recovery evidence already exists, the recovery-only Gate may update private Runtime Queue/Review bookkeeping and finish an already-journaled authorized Wiki transition. The Gate never starts a fresh transaction or chooses a no-journal action; only the separate explicit Recovery action coordinator can do so for an eligible state.

Project discovery is isolated to the current plugin and Vault lifecycle. During a plugin reload or Vault change, old project listeners and subscriptions are retired before the new project snapshot is installed. A scan or file operation that finishes late cannot republish its result into the new snapshot, and an old cleanup cannot release a newer write guard for the same path. Changing the configured Projects folder also invalidates old-folder scans, file events, and project edits synchronously; if a current-folder event wins a scan race, a trailing full scan converges the snapshot. This keeps Bundle discovery from inheriting stale or mixed Projects state across reloads and folder changes.

The internal safety core now carries a complete, content-addressed Manifest plan from compilation through durable review; the plan-bound final intent and plan digest then enter the transaction journal. Review filtering or content edits produce a new exact final projection instead of guessing from only the files that changed. Queue v5 keeps the accepted ChangeSet and final Manifest-intent identities with the exact applying claim, plus an append-only record when a user explicitly abandons an apply before journaling. Before a new apply can even inspect a target Wiki file, the runtime rechecks the Queue claim, full accepted Review payload and intent, source high-watermark, input-revision allocator, current Manifest read-set, and source commit ordering. Prepared-journal publication repeats that proof atomically, and the same complete reservation is preserved when the journal enters applying, whenever unfinished work is read during startup, throughout shared runtime updates while it is active, and before Manifest success and its replay ledger are published. A v3 reviewed apply that lacks the new intent identity, or a transaction whose Manifest read-set has drifted, is therefore blocked before any new Wiki file access rather than guessed into valid authorization. Retained reruns must describe the latest source observation, and a pending Queue commit marker must match the exact success ledger even after the active journal has been acknowledged. Exact ledger retry remains a byte-preserving no-op, while conflicting identity fails closed. Startup also cross-checks the Manifest, reserved commit metadata, latest ledger proof, Queue commit marker, and shared-page co-owner state. Shared pages update every recorded co-owner hash in that same operation. These guarantees now back the separate production reviewed-Apply coordinator: an explicit accepted create/update selection is revalidated before durable acceptance, claims the exact Queue job only after that preflight, repeats validation before transaction entry, and finalizes Manifest, ledger, Queue, and journal state through the commit coordinator. The Windows creator requires the page's parent folder to exist; a missing parent or a regular file in its place blocks Review submission without accepting the Review, creating a journal, or silently creating an untracked directory. Delete never enters this path.

When the compiler proves that no Wiki file needs to change, it does not fabricate an empty proposal or Review. The Runtime atomically completes the exact Queue attempt and advances a dedicated Manifest no-change marker that binds the source bytes, pipeline, input revision, compiler evidence, Manifest read set, and any previously generated pages. Existing accepted-page provenance remains unchanged. Because that Manifest update makes the current workflow plan stale, the worker refreshes its generation before touching more Queue work; even a lost write acknowledgement is resolved by rechecking the Manifest before retrying. A later exact-input observation can skip another model call only after production admission reads the latest Runtime-proven Apply or no-change outcome and hash-verifies every Manifest-authorized output. The reader accesses only those exact paths, returns no file content, and applies per-file and aggregate resource limits. A missing file, directory, or SHA-256 mismatch schedules a repair job or retained rerun; unavailable or unstable authority and I/O fail closed without mutating the Queue. Live events for tracked outputs re-observe their original source owners, including every owner of a shared page, while the cold full crawl provides the restart check. Output checks are deferred while Apply is in progress and repeated after the required generation refresh. A repair that proposes file changes still stops at Review and never overwrites or applies Wiki content automatically. If a repair instead claims `no_changes` while the authorized output is still stale, the Queue records a non-retryable unresolved repair rather than a success marker and suppresses repeated model work for that exact input until an up-to-date observation proves the output was restored; a genuinely newer source or pipeline remains eligible for normal work.

## Project Bundle configuration

Knowledge Bundle configuration is stored in the owning project's `project.md` frontmatter. The Projects layer preserves this value as untrusted data; only the knowledge startup boundary parses it. It never repairs paths or silently drops unknown fields.

```yaml
copilot-project-knowledge-bundle:
  version: 1
  id: research
  sourceRoots:
    - Sources/Research
  wikiRoot: Wiki/Research
  schemaRef: Knowledge/Schemas/research.md
  reviewMode: always
```

The object is strict: it accepts only the six fields shown above, requires at least one source root, and supports `always`, `multi_file`, or `trusted_generated_only` as the review mode. Review modes do not authorize automatic writes in the current milestone.

All paths must be canonical Vault-relative paths using `/`. Absolute paths, drive letters, UNC paths, backslashes, `.` or `..`, Windows-reserved names, invalid characters, and trailing dots or spaces are rejected rather than rewritten. Source roots must be unique under Windows case-insensitive comparison and must not overlap their Wiki root. A schema cannot live inside a generated Wiki.

Validation covers all configured projects together. Bundle IDs must be unique; Wiki roots cannot overlap one another; no Bundle's Wiki may overlap another Bundle's source roots; and no Bundle's schema may live inside another Bundle's Wiki. One invalid configuration keeps the whole knowledge workflow unavailable so two projects can never acquire ambiguous write ownership. If no project has this field, the Workspace lane reports the Bundle as unconfigured. If several valid Bundles exist, validation succeeds but the current milestone has no Bundle selector and does not choose one implicitly; keep the Bundle block in exactly one Project before Studio can be admitted. A settings or Project change synchronously invalidates the captured generation, closes its watcher/worker and exact Queue signal, and automatically starts a fresh startup generation while the plugin lifecycle remains active; a plugin reload is not required for this revalidation. During this ordinary hand-off, Studio shows a neutral, action-free **Refreshing Knowledge Studio…** state: prior load, command, Query, and citation authority has already been revoked, but the transition does not mean the preceding operation failed. Persistent configuration or Runtime startup problems remain fail-closed and appear on the guided Setup surface; durable Recovery and recoverable Sources states retain their dedicated surfaces.

## Import an external folder

Choose **Import folder** in the Knowledge Studio header to take a one-time snapshot of a folder selected explicitly through the system folder picker opened by Knowledge Studio. Import requires the live production generation, exactly one configured Bundle, and exactly one source root. It accepts `.md`, `.markdown`, `.txt`, and `.pdf` files owned by exactly one reviewed parser. Other files are counted and skipped without being read into Knowledge.

The selected root name and its nested relative paths are preserved below the Bundle source root. For example, selecting a folder named `Research` copies an eligible nested file to `<source root>/Research/<nested path>`. The picker does not provide or persist the external absolute path. Import only reads the selected originals; it never edits, renames, deletes, or synchronizes them. The resulting Vault files are exact `managed_copy` sources and are the durable source of record after import.

The complete selection is validated before its first file read, then eligible files are copied and registered sequentially. The current bounds are 1,000 selected files, 8 MiB per eligible file, 128 MiB across eligible files, and a 240-character Vault destination path. The per-file bound matches the current production parser policy. Windows case collisions and unsafe relative paths reject the selection. An absent destination is published with exact bytes; an existing exact-byte file is reused; an existing different file or directory is reported as a conflict and is never overwritten.

Each successful file remains durable if a later file conflicts or fails, so the receipt may be partial and an exact retry can resume safely. A batch that added registrations requests one Knowledge generation refresh after the pass rather than restarting once per file. The watcher then creates normal **Activity** work. When compilation proposes changes, it stops at **Review**, and only explicit acceptance can **Apply** generated Wiki changes; a proven `no_changes` result completes without fabricating a Review.

This feature intentionally replaces the earlier manual “move each external file into the source root” workaround. Knowledge does not provide a separate URL, browser-clipper, or single-file Windows Explorer import path; select the containing folder instead. The production stable-port path, exact retry, missing-copy repair, source immutability, Activity completion, and clean-console behavior have passed a bounded real-folder Windows run. The native system picker itself was not clicked during that run, and all compiler outcomes were `no_changes`; a physical picker interaction and a non-empty proposal taken through explicit Review and Apply remain separate acceptance work.

## Add a Vault source from Chat

Dragging a `.md`, `.markdown`, `.txt`, or `.pdf` file from Obsidian's Vault file explorer into Chat now shows an explicit **Use in this chat** / **Add to Knowledge** choice before either surface changes.

- **Use in this chat** adds the existing Vault file only to the current Chat context. It does not modify the Knowledge Manifest or start ingestion.
- **Add to Knowledge** registers the existing Vault file as a durable user-managed source without adding it to Chat context. A new registration refreshes the Knowledge workflow; the background job then appears in **Activity**. Choosing an already registered file leaves the durable identity unchanged.

Durable registration is enabled only on Windows after Knowledge reaches its live production generation, with exactly one configured Bundle and exactly one source root. The file must already be inside that source root and must be owned by exactly one reviewed production parser. The chooser accepts Vault Markdown, plain-text, and PDF files. A Vault PDF can remain temporary Chat context or become a durable Knowledge source. For external material, use Studio's folder-only **Import folder** action instead of Chat drag-and-drop.

## Create a Knowledge Draft from a completed AI response

A **Create Knowledge Draft** action is exposed only on a completed, non-error assistant message. User messages, error messages, and responses that are still streaming have no capture authority. Before opening the editor, Chat applies its copy-cleaning boundary so hidden reasoning/tool material is removed from the prefilled body. The title starts empty; both title and Markdown body remain editable, and submission requires an explicit reviewed checkbox.

Before editing, the stable capture port mints a frozen, generation-bound destination capability and the dialog displays its exact Bundle and source root. Submission cannot silently rebase onto a replacement generation or another Bundle. The user-authored payload remains exactly `{ title, body, reviewConfirmed: true }`; it does not contain a path, conversation history, user prompts, Chat context attachments, structured citations, or source provenance. The capture is therefore a user-reviewed secondary note, not a source-grounded Query result. Users should add the original book, chapter, page, or other verifiable locator before relying on it.

The pure capture renders `# <title>\n\n<body>` with one final newline, binds a deterministic digest and content hash, and accepts JavaScript `string.length` values of at most 200 for a trimmed single-line title and 1,000,000 for a non-empty body, plus at most 2,000,000 UTF-8 bytes in the fully rendered source. The production coordinator chooses `<sourceRoot>/Knowledge Draft <captureDigest>.md`; UI input cannot choose a Vault path. It uses the hardened exclusive file publisher and exact Manifest registration with `custody: managed_copy` and origin `chat_knowledge_draft`. Compiler authority remains ordinary `ingest`, not `query_writeback`.

A successful receipt proves only exact file publication and durable Source registration. The command itself has no model, Queue, Review, Apply, or Wiki-write capability. Its generation refresh lets the normal source watcher create later Activity work; compilation may call the configured Knowledge model and end in `no_changes` or a Review that still requires explicit acceptance and Apply.

The same exact title and body converge to the same content-addressed Source and an `already_registered` replay without overwrite. Changing either field creates a different capture identity and Source. After registration, an intentional edit of the Vault `managed_copy` is observed as a new revision of that Source; rename or deletion makes it Missing. Conflicting bytes are never overwritten. An uncertain failure or user stop request after exclusive publication but before observed registration may leave an unregistered exact orphan; the UI tells the user to inspect Sources/Activity, and a read-only registration confirmation or exact retry converges commit acknowledgement without inventing a Queue receipt. Once registration is durable, commit wins over a late generation replacement, caller abort, or refresh-reporting failure.

## Activity

Activity now loads the real durable Queue for the selected Bundle and distinguishes parsing, analysis, association, generation, validation, review, apply, and final commit acknowledgement. Pause, Resume, Cancel, and Retry are enabled only where the exact displayed Queue snapshot permits them. Every command submits the snapshot's Queue revision; a concurrent durable change makes the command stale instead of rebasing it onto newer work. Completion notifications request an authoritative reload rather than updating rows optimistically.

- **Pause** and **Resume** control whether the Bundle may start new work or accept a review. Pausing can durably pause and abort non-applying processing work; a transaction already applying is allowed to reach its recoverable commit boundary and is not interrupted halfway. Resume is available for ordinary user and rate-limit pauses and returns paused non-applying jobs to pending work.
- A Queue held by **Startup recovery**, **Recovery required**, or **Commit pending acknowledgement** cannot be cleared by ordinary Resume, another Pause, or a sequence of low-level Queue updates. Those gates preserve the current claim, job, pending-review anchor, and commit marker; an accepted review waiting to start is protected in the normal running state too. Transitions must match the exact current recovery operation, so an older successful ingest or a fabricated abandonment cannot replace the interrupted decision. A source capture now receives a globally unique retry-stable capture id, opaque token, and durable revision before asynchronous reading; the exact content hash and pipeline are then bound first-write-wins. The production Queue adapter can advance a high-watermark only when given that private token, consuming the exact binding in the same runtime-file update. A newer allocation that has not completed reading does not discard an older bound read, while a newer completed binding supersedes older unfinished observations. Pending allocated and bound work can be enumerated after restart; historical consumed retries return their own durable result without entering Queue again. A bound observation that has not reached Queue also blocks startup admission. Only conditional startup release can clear the exact startup-recovery gate after rechecking shared durable state. An authoritative cold-start crawl records a new observation revision even when source bytes are unchanged; content and pipeline deduplication prevent that observation from creating another job, model call, Review, or Wiki write.
- **Cancel**, **Retry**, and **Review** navigation are shown only when the selected job allows them. Cancel durably terminates pending, paused, or non-applying processing work. Retry returns a retryable, non-applying failed job to pending only when no active job for the same source exists and no newer source high-watermark carries different content or a different pipeline. Review navigation opens the durable proposal.
- A job awaiting review cannot use generic **Cancel**. It must leave through the Review path so its proposal outcome and any retained rerun stay consistent. The user may reject the proposal or explicitly submit eligible create/update selections for acceptance and Apply; neither path is automatic.
- A job being applied cannot be cancelled from the Activity panel.
- A committed job remains **Finalizing** until its durable commit marker has been acknowledged. It is not shown as completed early.
- A divergent interrupted write is shown as **Recovery required** and automatic writes remain blocked. The Recovery tab exposes **Continue** for `Accepted, not started`, and **Continue** or **Abandon** only for `Decision required`, where an apply claim exists but no transaction journal proves that writing began. Active, blocked, finalizing, Queue-level, and Vault-global transaction states expose only **Check again**. There is no generic rollback command.

Activity notifications only request a fresh durable read. They never promote a job optimistically.

## Change review

Review now displays live pending proposals from the durable Review Store. A record is visible only when it exactly matches the Queue's durable pending anchor and owning `awaiting_review` job. Before rendering, Studio observes every current target and builds a content-addressed Review snapshot; missing, occupied, directory, unavailable, or stale targets receive their fail-closed capabilities. Whole-proposal Reject remains content-free and performs no Wiki write. For eligible create/update changes, the user can explicitly accept a whole file, select changed blocks, or use **Accept all**; blocked targets cannot be forced into acceptance, and delete remains rejection-only.

The review surface sends only content-addressed snapshot identity plus opaque ChangeSet, file, and block identifiers back to the core. It never sends file paths, edited content, file before/after hashes, validation flags, or a claimed status. The Reject path accepts no content-bearing selection and performs no Wiki read or write. The separate reviewed-Apply coordinator reconstructs an accepted candidate from the durable proposal and those opaque decisions, recalculates target observations, and repeats deterministic structure, citation, OKF, link, source-artifact, Manifest, Queue, and transaction-authority checks before any create/update write.

The complete proposal is persisted in the Review Store before the queue can wait for review. Whole-proposal Reject re-proves the exact pending Review record, Queue job claim, durable pending anchor, proposal digest, and complete change-id set inside the Runtime. One atomic Runtime update advances the Review record to rejected, cancels the Queue job, removes its pending anchor, records the rejection tombstone, and promotes any exact retained rerun. An exact terminal retry is a byte-preserving no-op; an uncertain write is acknowledged only after rereading that exact final projection. Manifest state, transaction journal, apply ledger, and Wiki files are untouched by Reject. On explicit acceptance, the separate coordinator durably records the exact accepted projection, establishes the matching Queue apply claim, runs the recoverable create/update transaction, and uses the commit coordinator to finalize Manifest success, its replay ledger, Queue state, and journal acknowledgement.

For this milestone, a successful source commit must be backed by that durable accepted Review record. The configured auto-review modes are not allowed to publish knowledge success until a separate durable policy authorization is implemented; an in-memory policy decision is not sufficient.

Delete proposals are visible with a danger explanation but are rejection-only in this milestone. The Windows file store advertises `delete: false`; it can recognize an already-missing replay or a conflicting third state, but it never performs a delete. Create/update Apply now repeats its production validation immediately before the recoverable transaction, but delete acceptance stays disabled until a safe compare-and-delete implementation and delete-specific authorization and recovery checks exist.

Rejecting a proposal does not create an empty accepted ChangeSet, call a model, or write Wiki files. Its durable rejection identity remains available for safe retry and audit.

The applied-page inspector now separates the page's **Source Apply** baseline from its **effective** current head. **Known applied outputs** are deduplicated by exact content hash and retain ordered Source Apply and Forward revision origins; an exact body with both origins is shown as mixed rather than being relabelled as one origin. Proposal eligibility is explicit per row. The current file must still match its proven effective head, the selected row must not already be current, and the row's detail must remain within the supported bound. A Forward-only historical output cannot seed another proposal yet. A mixed-origin row is eligible only when its canonical detail authority is an ordinary Source Apply.

A historical-output proposal becomes a reviewed **Forward revision**, not a restore, rollback, or fresh compiler result. If its acceptance is durable but no journal or Wiki write has begun, **Accepted revision ready to apply** offers **Validate and apply** or **End without writing**. Ending records a truthful pre-write terminal outcome and creates no Wiki write, journal, apply ledger, or active overlay. Successful revisions can repeat on the same Bundle/source/page as one live-head chain: the Source-applied hash remains the immutable baseline, while each successor must compare-and-swap from the exact previous effective hash.

## Query

The **Query** tab appears only when the same live production generation has installed its read-only adapter. It searches the selected Bundle's current applied Wiki, not the whole Vault. The Manifest continues to preserve each page's last Source-applied content hash; an active, exact Forward overlay can make a later hash the page's effective current head. Query reads the exact effective bytes, so it neither mistakes the Source baseline for the current page nor invokes a model to repair, rewrite, or recompile a valid Forward revision. If any Forward page is orphaned, ambiguous, broken-lineage, or byte-mismatched, the complete Query snapshot fails closed after bounded retries. It neither filters only that page and continues nor silently falls back to the Source baseline; durable consistency must be restored before querying again.

Query first ranks exact applied-Wiki excerpts, including a proven Forward effective head, then re-proves their Markdown source locators without opening a note or changing the workspace. Wiki excerpts help the model interpret the question but are not citable evidence. A manually edited Forward body retains only the original Source citations: those citations prove their Source excerpts, not every new human-authored phrase. Only exact source excerpts that pass this fresh check receive request-local evidence IDs. With at least one eligible excerpt, the separate answer route makes one non-streaming DeepSeek JSON request. With none, Query returns **Insufficient evidence** with zero model requests. This normal grounded-answer request is distinct from model repair; merely reading an effective Forward head never starts a repair call.

Every displayed answer claim is explicitly labelled **Source fact** or **Inference** and must cite an evidence ID from that exact request. Core maps those IDs to opaque citation references; the model cannot create a source path, locator, or citation reference. Results are labelled **Supported**, **Partial**, or **Insufficient evidence** and may list evidence that is still needed. After the model returns, Query re-reads the complete applied-Wiki snapshot, including its source provenance, and re-proves every source citation actually used by the answer. Any Wiki, provenance, source, lifecycle, or cancellation drift rejects the result instead of publishing it.

Answer text is rendered as ordinary text, not model-controlled Markdown. An ordinary Query remains read-only. **Save to Wiki** appears only when the current result is **Supported** or **Partial**, contains at least one validated claim, and the same live generation exposes writeback. It is absent for retrieval-only and **Insufficient evidence** results. Starting a new query, manually refreshing Studio, receiving a durable reload hint, changing the active generation, or closing the plugin cancels or revokes older results, model work, citation references, and Save authority. Evidence-ID validation proves that every displayed citation came from an exact source excerpt supplied in this request; it does not make model interpretation infallible, so inspect cited excerpts for important decisions.

Saving accepts only a title from the UI; it does not accept a Wiki path or generated Markdown. The coordinator re-proves the current answer, applied-Wiki snapshot, and every citation actually used, then deterministically renders a content-addressed managed Markdown source beneath the uniquely configured source root. That capture embeds the original H.2 claims and evidence lineage. The production adapter creates the exact capture without overwriting an existing different file and registers the Manifest source with an exact `managed_copy` origin bound to the capture identity and content hash. It does not write a Wiki page and does not fabricate a queued receipt.

The real source watcher observes that registered capture, allocates the durable revision and Queue job, and the Compiler runs with `operation: query_writeback`. Any proposal must still appear in Review and receive explicit user acceptance before the existing recoverable transaction may Apply it. The first applied provenance points directly to the managed capture, while the embedded evidence preserves the earlier source chain. If the Schema proposes a page inside a nested Wiki folder, that folder must already exist on the current Windows adapter; Review submission reports the blocked preflight instead of implicitly creating a directory outside the transaction journal. An exact retry can converge after an uncertain create or registration result; a crash between creating the capture and registering it may leave an unregistered orphan capture, which is not treated as queued knowledge and requires later cleanup or exact retry.

A production Markdown citation button re-reads the exact `.md` source, checks its saved SHA-256 and quote locator, opens that note in Obsidian, and selects the proven exact quote. The navigator also validates line and heading locator types, but the current production text parser does not emit them. A PDF citation button requires a positive validated page, re-reads the exact `.pdf` as binary, compares its raw-byte SHA-256 with the durable locator, and then opens Obsidian's canonical `path#page=N` target. It repeats the byte proof after the asynchronous open and reports the citation as stale if the file changed. Neither path writes the source, Runtime, or Wiki. Retrieved PDF citations remain excluded from H.2 answer synthesis because the current answer route accepts only parser-reproved `.md` source excerpts; `.markdown` and `.txt` can be ingested but are not eligible answer evidence.

## Forward revisions and sticky recovery

One Bundle/source/page can carry repeated Forward revisions, but only one effective head is live. Each successor preserves the last true Source Apply hash and must use the predecessor's exact effective hash as its compare-and-swap before state. A later ordinary Source Apply supersedes the active Forward layer only when its successful commit proves the same source and exact target page. Applies to other pages and a truthful `no_changes` result preserve the Forward head; `no_changes` does not invent a successor Apply ledger.

Forward startup recovery is intentionally bounded. It always rechecks the exact current Wiki bytes first. Exact-after converges the durable committed result without writing again. **Recheck / retry exact Apply** makes at most one exact compare-and-swap per explicit command and is eligible only while a revision-one or revision-two journal still points to exact-before. **Keep current (no write)** never changes the Vault bytes and is refused for an ordinary exact-before state that still has a safe retry. When a no-write terminal is allowed, its durable outcome follows the journal phase: abandoned before write for revision one, uncertain write followed by external supersession for revision two, or committed followed by external supersession for revision three. It does not relabel every phase as external supersession or pretend Apply succeeded. The product has no force-overwrite path.

The current Forward `recovery_required` card exposes **Recheck / retry exact Apply** and **Keep current (no write)**. Both commands use the row's current opaque snapshot identity and re-observe the file inside the recovery boundary; they never trust a UI claim about its bytes. While either command is running, both controls are disabled until durable truth reloads. A rejected keep-current request means zero-write terminalization is not safe from the newly observed state; do not bypass that result by editing private state.

## What comes next

Startup reconciliation for persisted work is now invoked by the plugin through a recovery-only production composition. After strict Runtime, Projects, aggregate Bundle, and zero-network preflight checks, the outer barrier runs the inner Gate for every configured Bundle, with any Vault-global active transaction owner first. The Gate can recover the Queue, roll forward only an already-journaled transaction and its commit bookkeeping, reconcile pending or rejected Review hand-offs, and then read the Queue, the Vault-global transaction slot, and every accepted Review classification from one runtime-envelope snapshot. A Review revision change restarts this bounded pass. Runtime and Queue observations may only advance; a rollback or different Queue content at the same revision fails closed. Every accepted Review action must also correlate one-to-one with exactly one classification through its opaque recovery id. The first file-state conflict is persisted as sticky recovery state and immediately re-read as the same visible blocker. Missing transaction ownership, malformed Runtime state, and unavailable recovery dependencies remain sanitized startup failures rather than being guessed into safety.

Accepted reviews are never started or applied automatically by the startup Gate. Only an explicit Review submission can durably accept eligible create/update selections, establish the exact Queue apply claim, run the recoverable transaction, and finalize it. If acceptance became durable but the apply claim was not started, Recovery shows **Continue** only. If the claim exists but no journal was ever published, Recovery shows **Continue** and **Abandon**: Continue reloads the accepted content and rechecks the current Manifest before the transaction may inspect Wiki files; Abandon is allowed only when the same atomic update proves that no active journal, commit marker, or source-input success ledger exists, and it keeps the accepted review as immutable history. A stale Manifest blocks Continue but does not fabricate evidence that Wiki writes began. Once a transaction is active, blocked, or finalizing—or when only Queue-level or Vault-global recovery evidence is available—the Studio can only recheck durable state. It does not offer a generic rollback or guess that a write can be undone.

An `observed_clear` gate result is only an optimistic display observation. The new conditional release core carries its Runtime, Review, and Queue revisions into one shared-envelope update, where it rechecks the Vault-global transaction, recovery markers and claims, interrupted apply work, cross-Bundle write-recovery evidence, and every accepted Review classification. Only `committed` or `abandoned` accepted records are terminal. Success changes only the exact `startup_recovery` Queue control and the Queue/Runtime revisions; stale or blocked attempts preserve the runtime file bytes. If the write committed but the caller observed an error, the old token is deliberately not treated as a receipt: startup must run again and the fresh observation will see the Queue already running. A pre-existing user or rate-limit pause is preserved byte-for-byte on cold start after the same safety proof, yet that unchanged result still admits the current live watcher, worker, and Studio generation. It does not implicitly Resume the Queue or grant Apply authority.

The recovery-only Gate now appears in Studio as clear, attention-required, blocked, or unavailable startup state. Attention or blocked state retains a recovery-only Studio adapter and opens the Recovery tab with only the actions justified by the exact atomic Runtime projection. A clear recovery result starts the same-generation observation session; after convergence it performs the fresh Gate/conditional-release handshake. Successful admission installs the exact generation-owned worker, schedules it from durable Queue events and retry times, and publishes the same-generation Studio adapter and reviewed-Apply command boundary. An empty/running Queue or retained user/rate-limit pause is not sufficient by itself; worker and Studio publication still require the exact conditional-release proof and current generation health.

The oldest runtime format is upgraded only when its restricted migration proof succeeds; incompatible legacy state still fails closed instead of being guessed into a newer shape. The version 3 to version 4 migration is broader but equally conservative: it preserves active and recovery state, accepted Apply history, observations, attempts, and high-watermarks, while returning only an unproved current completion to pending recovery work. Restarting that migration is idempotent.
