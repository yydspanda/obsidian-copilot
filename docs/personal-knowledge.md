# Personal Knowledge Studio

Knowledge Studio is the Windows desktop workspace for the personal knowledge system being built into this Copilot fork. It is designed to make long-running ingestion, multi-file review, and recoverable knowledge maintenance understandable before any generated page is written.

## Platform and availability

The Knowledge Studio view and ribbon entry are available only in Obsidian Desktop on Windows. Open it from the library icon in the ribbon or run **Open Knowledge Studio** from the command palette. The command remains registered on other platforms so it can explain that the feature is unsupported; it does not open the Studio there.

The rest of Copilot keeps its existing platform support. The plugin manifest therefore remains compatible with mobile and other desktop systems; the Knowledge Studio view and navigation are not registered outside Windows. This avoids disabling Chat for existing users while the new filesystem and recovery adapters are deliberately tested on Windows first.

The current milestone exposes a fail-closed Studio shell and the review/activity foundations. On supported Windows desktop installations, the plugin now attempts to initialize and validate a private `knowledge-runtime-v1.json` state foundation beside the plugin files. The filename remains stable while its internal format is explicitly versioned; the current outer format is version 3.

After Obsidian reports that the Vault layout is ready, a plugin-level startup barrier checks the Runtime, waits for Projects to finish loading, and strictly validates every project-owned Knowledge Bundle as one Windows write-boundary set. The Studio uses one stable delegating port across this lifecycle, so an already-open view cannot retain an obsolete adapter. Missing, invalid, or conflicting configuration receives an explicit unavailable explanation. A valid configuration also runs a synchronous production preflight over the exact Bundle owners, current Projects/settings snapshot, reviewed parser/compiler profile, selected DeepSeek V4 model, hydrated credential, and the plugin renderer's native-fetch capability. Preflight only proves that a private route can be constructed; it never invokes fetch. Startup then consumes one recovery-only capability over that exact Runtime, Vault, and Bundle generation. A Vault-global active transaction owner is recovered first; the Gate may reconcile already-durable Queue/Review bookkeeping and roll forward only an already-persisted, already-authorized transaction journal. Settings, Projects, Runtime, replacement, or unload invalidation is rechecked between durable recovery phases, so an obsolete generation cannot finish Queue recovery and then begin a Wiki transaction. A phase that already entered durable reconciliation is allowed to reach its crash-safe boundary before later phases stop. The Gate cannot release the Queue, claim new work, choose a no-journal recovery action, prepare a new transaction, start a watcher or worker, or call a model. **Recovery needs attention**, **Recovery blocked**, and recovery failure remain separate fail-closed states. Even an `observed_clear` result remains **Adapter unavailable** until conditional release and the complete workflow are connected. The shell shows no fabricated jobs and cannot generate new knowledge; only pre-existing journaled work may be completed to its recorded recoverable boundary.

An independent Vault source-watcher adapter, strict plan builder, read-only workflow-plan loader, listener-first observation-startup Core, and job-bound model-adapter core are now implemented and covered by automated tests, but they are intentionally not activated by plugin startup yet. The watcher no longer accepts a caller-created list of paths and hashes. The loader builds its opaque plan from strictly detached Bundle and current Manifest snapshots, exact schema bytes, the reviewed parser registry, and a projected model behavior profile. An internal production composer now binds those inputs to the exact preflight generation and a startup-held enqueue-only Queue. It establishes listeners before its crawl, reconciles recoverable allocated and bound observations, performs an authoritative full scan, waits for captures to settle, and can repeatedly re-prove the live session before later startup phases. It cannot release or execute Queue work. This composer is tested but is not connected to the plugin startup workflow. Model selection is exact and never falls back to a different chat model. Only an explicit behavior allowlist is retained; API keys, complete settings, unknown model fields, and credential-like compiler or parser configuration are not included. Endpoint and routing values are retained only as plaintext-free SHA-256 identities; these hashes are not credentials, and low-entropy values may still be enumerable.

Plan construction verifies that every registered source remains inside an authorized source root, never ingests its generated Wiki or schema, and maps to exactly one configured parser. Each source fingerprint binds the exact Bundle-config digest, compiler version and configuration, selected parser identity and configuration, exact schema hash, projected model behavior, output language, OKF version, and citation contract. The plan also binds the selected parser profile, Manifest revision and digest, and submitted profile digest without exposing schema content, settings, App/Vault services, or parser capabilities. The loader reads all Bundle authorities twice and publishes a plan only when both complete projections match. An opaque execution owner is registered exclusively to one Runtime and one workflow-loader generation, so equal data or deliberate reuse of the same owner cannot join different lifecycles. This detects changes during collection but is not a cross-Bundle database transaction, so the owning workflow generation must still invalidate the plan whenever Projects, settings, Runtime, App, or Vault ownership changes.

Before a source is parsed, Queue now issues an opaque process-local claim bound to the exact active controller, attempt, QueueStorage facade, and Queue-owned cancellation signal. Runtime accepts that claim only through a narrow proof facade and reads the unique processing Queue job, exact consumed source observation, and current Manifest from one atomic envelope. A scalar high-watermark or a migrated legacy checkpoint is not sufficient. The authorization binder then compares Runtime's Manifest authority with the workflow plan before any source read. The plan rechecks the current Manifest, exact schema bytes, and secret-free pipeline profile, asks the exact-byte reader to prove the source hash, and repeats those authority reads after parsing. Only this Runtime-to-workflow-to-Runtime proof sandwich can upgrade parsed material into an opaque compiler preparation; a job-shaped object, copied prototype, or `unbound_read_only` marker cannot do so.

The same returned byte array is passed to a Knowledge-specific parser; the existing general file parser is not reused because it can reread paths or use caches and external services. The first built-in parser accepts only bounded, non-empty UTF-8 text for explicitly configured suffixes. It preserves BOM, CRLF, Chinese, and other Unicode text byte-for-byte and rejects malformed UTF-8. The execution binding detects byte changes that remain at its parser-boundary checkpoints; parser registration and fingerprinting do not sandbox an untrusted parser or detect a mutate-then-restore implementation. Production composition must therefore use only owned, reviewed parser capabilities. PDF and other binary formats are not yet supported by this boundary.

The Knowledge-specific model adapter accepts only that authentic preparation, its exact Queue signal, a matching secret-free model profile, an opaque private route capability, and a one-shot call authorization issued internally by the Compiler for the exact request. One authorized preparation can create only one adapter. Every `compile()` invocation receives a fresh opaque session: the adapter pins it during analysis, and generation must present the same identity, preventing duplicate adapters, cross-Compiler, cross-compile, and replayed stage composition. Credentials, endpoint text, and the transport closure remain in module-private memory; the public route exposes only its detached profile declaration. The complete configuration digest binds model parameters plus endpoint/routing identities. A concrete route can additionally bind the complete pipeline profile so output language, compiler/parser behavior, OKF, and citation-contract changes cannot reuse an otherwise identical model route. For each authorized stage, the adapter makes one outer route invocation, re-proves authority before and after it, accepts only bounded JSON text, parses it inside the private boundary, and returns a detached bounded object to the Compiler's strict schema parser. A fresh adapter currently pins the first authentic Compiler session it receives, so it is a trusted assembly capability until that first call. The future production composer must hand it directly to the intended Compiler before other code can observe it, or introduce a separate composer-issued pre-bind owner.

An isolated DeepSeek route and deterministic two-stage Knowledge prompt encoder are now implemented. They are not shared with Chat, LangChain, `safeFetch`, or Obsidian `requestUrl`. The route accepts only the reviewed official `https://api.deepseek.com/chat/completions` endpoint and the current `deepseek-v4-flash` or `deepseek-v4-pro` model identities. Saved direct-DeepSeek `deepseek-chat` and `deepseek-reasoner` entries are retained as disabled migration markers, and an old chat, command, or project reference is never silently redirected. It sends one POST per authorized stage through an injected native-fetch-compatible port with the exact Queue cancellation signal, `stream: false`, no tools, no fallback, no internal retry, and `response_format: { type: "json_object" }`. DeepSeek JSON Object mode is not a native JSON-Schema guarantee: the versioned prompt includes the expected shape and a minimal JSON example, while the existing strict Core schema remains authoritative. Source text, schema text, existing Wiki content, and output-language values stay inside canonical escaped `INPUT_JSON`; they never become system-message instructions. The Schema text is treated only as a constrained Wiki organization, terminology, content, and formatting policy—it cannot change output shape, authority, identifiers, paths, evidence rules, or the higher system contract. Other source/context strings remain untrusted data. The response is counted from its first byte, including non-stream keep-alive whitespace, capped before fatal UTF-8 decoding, and accepted only for one exact-model choice ending in `stop` with bounded token usage. Thinking mode rejects configured `topP` and requires an explicit zero temperature placeholder, then omits both sampling fields from the wire because DeepSeek does not support them in that mode; non-thinking mode may send the validated sampling fields. Fenced JSON, repair, redirects, SSE, truncated output, tool calls, old model aliases, custom endpoints, and unsupported settings fail closed. Sanitized transport categories cross the private adapter boundary without retaining provider payloads or causes: an authentic 429 can become the Queue's durable rate-limit pause, 500/503 and network failures remain bounded Queue retries, and authentication, balance, request, or invalid-response failures terminate. The transport itself still retries nothing. See the current [DeepSeek Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion/), [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/), and [JSON Output](https://api-docs.deepseek.com/guides/json_mode/) contracts.

This foundation does **not** mean files are currently being watched, parsed, or sent to a model in the background. Startup preflight reads only the exact already-hydrated credential required by the selected model, constructs the private route, and performs zero fetch calls; it never writes the key to a descriptor, result, prompt, error, log, or durable Runtime file. The internal observation composer has no `main.ts` integration, executor access, or worker, so it is inactive in the current plugin. When it is activated, a source already missing at startup, an exact-path case mismatch, a Windows path-key collision, a capture failure, or an observed rename/delete becomes an authoritative blocker for that plan generation rather than an empty-file observation. A restart crawl can prove current file state, but there is still no durable receipt for a destructive event that happened while the plugin was stopped. Conditional startup release and the compiler worker also remain unconnected. Studio therefore remains **Adapter unavailable**. This milestone performs no provider request, background Queue execution, or new Wiki transaction. When durable recovery evidence already exists, the recovery-only Gate may update private Runtime Queue/Review bookkeeping and may finish an already-journaled authorized Wiki transition; it never starts a fresh one.

Project discovery is isolated to the current plugin and Vault lifecycle. During a plugin reload or Vault change, old project listeners and subscriptions are retired before the new project snapshot is installed. A scan or file operation that finishes late cannot republish its result into the new snapshot, and an old cleanup cannot release a newer write guard for the same path. Changing the configured Projects folder also invalidates old-folder scans, file events, and project edits synchronously; if a current-folder event wins a scan race, a trailing full scan converges the snapshot. This keeps Bundle discovery from inheriting stale or mixed Projects state across reloads and folder changes.

The internal safety core now carries a complete, content-addressed Manifest plan from compilation through durable review; the plan-bound final intent and plan digest then enter the transaction journal. Review filtering or content edits produce a new exact final projection instead of guessing from only the files that changed. Queue v5 keeps the accepted ChangeSet and final Manifest-intent identities with the exact applying claim, plus an append-only record when a user explicitly abandons an apply before journaling. Before a new apply can even inspect a target Wiki file, the runtime rechecks the Queue claim, full accepted Review payload and intent, source high-watermark, input-revision allocator, current Manifest read-set, and source commit ordering. Prepared-journal publication repeats that proof atomically, and the same complete reservation is preserved when the journal enters applying, whenever unfinished work is read during startup, throughout shared runtime updates while it is active, and before Manifest success and its replay ledger are published. A v3 reviewed apply that lacks the new intent identity, or a transaction whose Manifest read-set has drifted, is therefore blocked before any new Wiki file access rather than guessed into valid authorization. Retained reruns must describe the latest source observation, and a pending Queue commit marker must match the exact success ledger even after the active journal has been acknowledged. Exact ledger retry remains a byte-preserving no-op, while conflicting identity fails closed. Startup also cross-checks the Manifest, reserved commit metadata, latest ledger proof, Queue commit marker, and shared-page co-owner state. Shared pages update every recorded co-owner hash in that same operation. These guarantees are implemented and tested as foundations, but they do not make the unavailable Studio workflow usable yet.

The runtime foundation has automated contract and filesystem tests, but it has not yet passed acceptance inside a real Windows Obsidian test Vault. In particular, Obsidian process serialization, plugin reloads, external editor races, NTFS/OneDrive behavior, and crash persistence still need real-device verification. It must not be treated as production-ready durable storage yet.

## Project Bundle configuration

Knowledge Bundle configuration is stored in the owning project's `project.md` frontmatter. The Projects layer preserves this value as untrusted data; only the knowledge startup boundary parses it. It never repairs paths or silently drops unknown fields.

```yaml
copilot-project-knowledge-bundle:
  version: 1
  id: research
  sourceRoots:
    - Sources/Research
  wikiRoot: Wiki/Research
  schemaRef: Knowledge/Schemas/research.md
  reviewMode: always
```

The object is strict: it accepts only the six fields shown above, requires at least one source root, and supports `always`, `multi_file`, or `trusted_generated_only` as the review mode. Review modes do not authorize automatic writes in the current unavailable milestone.

All paths must be canonical Vault-relative paths using `/`. Absolute paths, drive letters, UNC paths, backslashes, `.` or `..`, Windows-reserved names, invalid characters, and trailing dots or spaces are rejected rather than rewritten. Source roots must be unique under Windows case-insensitive comparison and must not overlap their Wiki root. A schema cannot live inside a generated Wiki.

Validation covers all configured projects together. Bundle IDs must be unique; Wiki roots cannot overlap one another; no Bundle's Wiki may overlap another Bundle's source roots; and no Bundle's schema may live inside another Bundle's Wiki. One invalid configuration keeps the whole knowledge workflow unavailable so two projects can never acquire ambiguous write ownership. If no project has this field, Studio reports **Bundle unconfigured**. If several valid Bundles exist, validation succeeds but the current milestone does not choose one implicitly; Studio remains unavailable until an explicit Bundle selector is added. A settings or Project change synchronously invalidates the captured preflight and recovery generation; configuration changes currently require a plugin reload before the startup-only check runs again.

## Activity

The following Activity behavior is implemented in the core and UI, but the unavailable Studio shell does not yet load real jobs. Activity is designed as a read-only projection of the durable ingest queue. It distinguishes parsing, analysis, association, generation, validation, review, apply, and final commit acknowledgement.

- **Pause** and **Resume** control whether the Bundle may start new work or accept a review. A transaction already applying is allowed to reach its recoverable commit boundary and is not interrupted halfway.
- A Queue held by **Startup recovery** cannot be cleared by ordinary Resume, another Pause, or a sequence of low-level Queue updates. Startup, interrupted-apply, and commit-acknowledgement recovery gates preserve the current claim, job, pending-review anchor, and commit marker; an accepted review waiting to start is protected in the normal running state too. Transitions must match the exact current recovery operation, so an older successful ingest or a fabricated abandonment cannot replace the interrupted decision. A source capture now receives a globally unique retry-stable capture id, opaque token, and durable revision before asynchronous reading; the exact content hash and pipeline are then bound first-write-wins. The production Queue adapter can advance a high-watermark only when given that private token, consuming the exact binding in the same runtime-file update. A newer allocation that has not completed reading does not discard an older bound read, while a newer completed binding supersedes older unfinished observations. Pending allocated and bound work can be enumerated after restart; historical consumed retries return their own durable result without entering Queue again. A bound observation that has not reached Queue also blocks startup release. Only the conditional startup release can change the final startup gate to running after rechecking the shared durable state.
- **Cancel**, **Retry**, and **Review** are shown only when the selected job allows them.
- A job awaiting review cannot use generic **Cancel**. It must be accepted or durably rejected from Review so its proposal outcome and any retained rerun stay consistent.
- A job being applied cannot be cancelled from the Activity panel.
- A committed job remains **Finalizing** until its durable commit marker has been acknowledged. It is not shown as completed early.
- A divergent interrupted write is shown as **Recovery required** and automatic writes remain blocked. This milestone shows the blocker but does not yet expose revalidate, continue, rollback, or abandon actions.

Activity notifications only request a fresh durable read. They never promote a job optimistically.

## Change review

The following Review behavior is implemented in the core and UI, but it is not yet connected to a live Windows workflow. Review presents one proposed ChangeSet across all of its files. Create and update proposals can be accepted exactly, rejected, or decided block by block. Batch actions still respect every file's capability: **Accept all** cannot override a blocked target.

The review surface sends only content-addressed snapshot identity plus opaque ChangeSet, file, and block identifiers back to the core. It never sends file paths, edited content, file before/after hashes, validation flags, or a claimed status. The core reconstructs the exact selected content, recalculates hashes, and runs deterministic validation again.

The complete proposal is persisted in the Review Store before the queue can wait for review. Accept or Reject then persists an exact terminal Review Store record before the queue changes state. Refreshing the same acceptance while its apply claim is still active is safe and does not create another claim; a conflicting receipt is blocked. After an apply is fully finalized, a late acceptance is not applied again and will be handled by the future Review/Manifest reconciliation flow.

For this milestone, a successful source commit must be backed by that durable accepted Review record. The configured auto-review modes are not allowed to publish knowledge success until a separate durable policy authorization is implemented; an in-memory policy decision is not sufficient.

Delete proposals are visible with a danger explanation but are rejection-only in this milestone. The Windows file store advertises `delete: false`; it can recognize an already-missing replay or a conflicting third state, but it never performs a delete. Manifest ownership, source provenance, and last-generated hashes are now journaled and revalidated, but delete acceptance stays disabled until a safe compare-and-delete implementation and the remaining schema/link/source-artifact dependencies are also revalidated immediately before write and recovery.

Rejecting a proposal does not create an empty accepted ChangeSet and does not write files. Its durable rejection identity remains available for safe retry and audit.

## What comes next

Startup reconciliation for persisted work is now invoked by the plugin through a recovery-only production composition. After strict Runtime, Projects, aggregate Bundle, and zero-network preflight checks, the outer barrier runs the inner Gate for every configured Bundle, with any Vault-global active transaction owner first. The Gate can recover the Queue, roll forward only an already-journaled transaction and its commit bookkeeping, reconcile pending or rejected Review hand-offs, and then read the Queue, the Vault-global transaction slot, and every accepted Review classification from one runtime-envelope snapshot. A Review revision change restarts this bounded pass. Runtime and Queue observations may only advance; a rollback or different Queue content at the same revision fails closed. Every accepted Review action must also correlate one-to-one with exactly one classification through its opaque recovery id. The first file-state conflict is persisted as sticky recovery state and immediately re-read as the same visible blocker. Missing transaction ownership, malformed Runtime state, and unavailable recovery dependencies remain sanitized startup failures rather than being guessed into safety.

Accepted reviews are never started or applied automatically by this gate. The real pipeline test now also covers an accepted Review before apply starts and proves the safely paused runtime bytes and Wiki remain unchanged. An explicit exact acceptance may establish its apply claim while leaving the startup gate paused; this does not release unrelated backlog. If that claim exists but no journal was ever published, the core requires an explicit **Continue** or **Abandon** decision. Continue reloads the accepted content and rechecks the current Manifest before the transaction may inspect Wiki files. Abandon is allowed only when the same atomic update proves that no active journal, commit marker, or source-input success ledger exists; it keeps the accepted review as immutable history. A stale Manifest blocks Continue but does not fabricate evidence that Wiki writes began.

An `observed_clear` gate result is only an optimistic display observation. The new conditional release core carries its Runtime, Review, and Queue revisions into one shared-envelope update, where it rechecks the Vault-global transaction, recovery markers and claims, interrupted apply work, cross-Bundle write-recovery evidence, and every accepted Review classification. Only `committed` or `abandoned` accepted records are terminal. Success changes only the exact `startup_recovery` Queue control and the Queue/Runtime revisions; stale or blocked attempts preserve the runtime file bytes. If the write committed but the caller observed an error, the old token is deliberately not treated as a receipt: startup must run again and the fresh observation will see the Queue already running. Existing user or rate-limit pauses are never overwritten.

The recovery-only Gate now appears in Studio as clear, attention-required, blocked, or unavailable startup state, but recovery decisions and conditional release are still not connected. There is intentionally no worker to release. The next plugin-owned workflow must activate the internal observation composer for the same Runtime and preflight generation, keep its live health proof current, add complete artifact and projection validators, and then run conditional release from a fresh Gate observation before installing a ready delegate. An empty/running Queue or a retained user/rate-limit pause is not by itself proof that startup coordination and release completed.

Only a provably idle legacy runtime is upgraded automatically. A legacy file containing active/recovery work, prior Manifest success, an apply abandonment, or reserved commit metadata is kept byte-for-byte and loading fails closed rather than guessing it into the new format; a user-facing recovery path is still future work.

The next implementation steps are activating the internal observation session behind the startup barrier, rerunning a fresh Gate while that session remains healthy, applying conditional release, and only then composing the full file/compiler worker and enabling Resume. Bundle selection, a Studio recovery screen, durable `no_changes` semantics, durable authorization for any future auto-apply policy, the remaining schema/link/source-artifact read-set, coordinated Queue/Review/observation history retention, future byte-only PDF/binary parsers, Chat's **Add to Knowledge** entry, grounded query/citation navigation, and end-to-end testing in a dedicated Windows Vault also remain. The Studio should not be treated as a finished ingestion workflow until those integrations and tests are complete.
